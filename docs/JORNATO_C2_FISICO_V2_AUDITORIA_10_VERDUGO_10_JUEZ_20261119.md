## I. VERDUGO: diez pasadas para refutar la orden inicial

| Pasada | Foco y acción realizada | Hallazgo adversarial sustentado | Decisión concreta |
|---|---|---|---|
| **V01** | Contraste de autorización con riesgos del celular | «Usa el celular» autoriza QA, no acceder a datos personales, borrar aplicaciones o cambiar configuración. La versión anterior era correcta aquí, pero no imponía una puerta previa al efecto del runner. | Mantener autorización acotada; exigir preflight **antes** de cualquier instalación o test. |
| **V02** | Examiné el supuesto «app instalada con datos» | `pm list packages` revela presencia del paquete, **no si su almacenamiento contiene datos de usuario**. Un instalador con firma compatible igualmente puede sobrescribir software existente. | Si paquete exacto existe y no hay constancia inequívoca de QA desechable, **BLOCKED_PACKAGE**; no intentar descubrir datos privados. |
| **V03** | Ataqué el flujo de `flutter test` | La orden verificaba `adb install` manual, pero el test runner puede instalar/reemplazar o limpiar sus propios paquetes. Hay riesgo de efectos colaterales no inventariados. | Inspeccionar dos APK/package IDs, flavor y teardown **antes de ejecutar**; un solo mecanismo de instalación sin doble instalación. |
| **V04** | Confronté flavor/`applicationId` | `productDebug` es un artefacto histórico; la ejecución automática puede usar otro flavor por defecto. Test sobre paquete distinto no prueba el build pretendido. | Resolver `applicationId`/sufijo/flavor desde Gradle y artefacto reales; usar destino `-d <serial>` y flavor real, no suponer valores. |
| **V05** | Revisé el diff C2 de instrumentación | El test abre base con/ sin contraseña read-only y una copia corrompida, pero debe demostrarse que esos paths son del paquete ficticio. El namespace fijo podría haber sido usado antes. | Probar aislamiento de datos antes de correr el test; reparar únicamente colisión reproducida, no borrar storage para obtener PASS. |
| **V06** | Examiné inferencia criptográfica | `cipher_version`, cabecera opaca y camino FlutterSecureStorage no prueban por sí solos hardware-backed Keystore/attestation. | Separar prueba de motor cifrado, prueba de ruta plugin/Keystore y prueba de hardware; `NOT_RUN` para attestation sin evidencia. |
| **V07** | Revisé rechazo de corrupción | En C2 se altera un byte en offset 100 y se consulta `sqlite_master`: la región dañada podría no ser evaluada; el test podría ser inconcluso. | Si falla el oráculo, ajustar **solo copia sintética y test focal**; nunca tocar DB productiva ni atribuir bug al motor automáticamente. |
| **V08** | Cuestioné el reinicio del proceso | Un `am force-stop` ejecutado durante la misma instrumentación mata la aplicación/controlador, por lo que el propio test no puede continuar garantizando readback. | Exigir mecanismo **dos etapas preexistente** sin reinstalación/clear; si falta, `BLOCKED_HARNESS`, no PASS falso. |
| **V09** | Cuestioné `PASS_PHYSICAL_SCOPED` | La versión previa permitía PASS con algunos gates nativos ejecutados aunque restart/tenant siguieran pendientes. Riesgo de inflar el dictamen. | Declarar PASS_PHYSICAL_SCOPED **solo** para cuatro gates centrales + restart y aislamiento del paquete; los demás expresamente bloqueados. |
| **V10** | Verifiqué terminación y trazabilidad | WIP con archivos untracked; SHA de estado Git no demuestra conservación de bytes. Un ZIP puede omitir origen o mezclar log/source hash. | PRE/POST por archivo exacto, logs sanitizados, manifiesto no autorreferente y **un solo ZIP**; H9 global NO_GO. |

## II. JUEZ: diez pasadas para cuestionar las correcciones propuestas

| Pasada | Objeción o alternativa juzgada | Razonamiento en contra y a favor | Dictamen |
|---|---|---|---|
| **J01** | ¿La seguridad de paquete bloqueará demasiado? | Si el paquete **no está instalado** y la ruta de prueba es sintética, se permite instalar; si está instalado y hay datos desconocidos, el permiso genérico no habilita sobrescribir. | **CONFIRMAR** la puerta de paquetes sin bloquear un primer uso limpio. |
| **J02** | ¿Mejor crear un flavor exclusivo ahora? | Evitaría colisiones, pero agregaría otra configuración Android y puede cambiar app/prod bajo QA. No fue autorizado como solución estructural. | **RECHAZAR** nuevo flavor; reutilizar el que ya existe o bloquear si no es seguro. |
| **J03** | ¿Basta con escoger serial ADB? | Seleccionar `-s` evita otro dispositivo, pero no previene el impacto sobre apps del mismo teléfono. Ambos controles son necesarios. | **CONFIRMAR** serial explícito + paquete exacto. |
| **J04** | ¿Pedir una copia total del teléfono? | Sería invasiva, arriesgaría datos personales y no es necesaria para un paquete QA inicialmente ausente. | **RECHAZAR** backup/logcat global; evidencia mínima por paquete. |
| **J05** | ¿Reescribir la prueba de cifrado para máxima cobertura? | Ya hay test C2 con aperturas y copia corrupta; modificarlo sin ejecución reincidiría en el ciclo de auditoría y código sin QA. | **RECHAZAR** rediseño; corregir solo si la ejecución demuestra brecha. |
| **J06** | ¿Declarar PASS_KEYSTORE por usar el plugin? | Usar `FlutterSecureStorage` en Android demuestra el recorrido del plugin bajo prueba, pero no atestación de hardware. | **CONFIRMAR** separación `PASS_PLUGIN_PATH` / `PASS_KEYSTORE_VERIFIED` / `HARDWARE_ATTESTATION=NOT_RUN`. |
| **J07** | ¿Crear un driver externo para probar force-stop? | Un driver nuevo aumentaría ruido y podría reinstalar el paquete, violando preservación de datos. Si no existe soporte, reconocer límite. | **RECHAZAR** nuevo framework; usar dos fases existentes o `BLOCKED_HARNESS`. |
| **J08** | ¿Reejecutar los 75 tests por precaución? | No cambió el contrato host solo por autorizar hardware; sí se permite regresión focal si se altera el propietario de la lógica. | **RECHAZAR** rerun ritual, **ACEPTAR** test vecino tras delta real. |
| **J09** | ¿Quitar C2 y pasar directamente a sincronización Pro? | Pro necesita credenciales/tenant QA autorizados, ausentes; hacerlo ahora produciría bloqueos y superficie de riesgo. | **RECHAZAR** giro hacia Pro. Mantener C2 y `BLOCKED_CONTRACT`. |
| **J10** | ¿Aprobar H9 al pasar cuatro subpruebas? | El objetivo es lanzar, pero Android persistente/reinicio, tenant/Pro y permisos restantes no quedan certificados por cuatro checks. | **CONFIRMAR** aceptación estrictamente acotada, H9/release NO_GO, vuelta al Director tras ZIP. |
